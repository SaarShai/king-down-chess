# Hosting

The facts for the live site, its domain and the secret files. Every deploy publishes to the world: deploy only what the owner asked to put online.

## Site

- The game is public at https://kingdown.vercel.app and https://kingdown.dev.
- Vercel project `kingdown`, team "Saar's projects" (`saars-projects-2c777ec5`), Pro plan. The Vercel CLI on this Mac is signed in.
- The site, the website API and internal jobs use project `kingdown` at `https://kingdown.dev` (release, 2026-10-19). The ChatGPT plugin (MCP and OAuth) is parked: see [Parked: the ChatGPT plugin](#parked-the-chatgpt-plugin). The separate `kingdown-plugin` project is the old target. ## Deploy

- `tools/deploy.sh` is the only deploy path. Do not run the Vercel CLI yourself.
- The release builds from GitHub main: the remote `origin` is `github.com/SaarShai/king-down-chess`. The script stops with a clear message when `origin` is absent.
- Production profile (staging-first-game ticket 66): `tools/deploy.sh` serves production only, and `node tools/deploy-staging.mjs` serves staging only. Every mode refuses a shell with `KINGDOWN_STAGE` or `VITE_KINGDOWN_STAGE`. A website run needs `VITE_SUPABASE_URL` set to the production account origin (`https://utqzovjmclfyojedmwok.supabase.co`) and the production `VITE_SUPABASE_PUBLISHABLE_KEY` (a public `sb_publishable_` value); only the site build gets them. The script refuses a build with the staging manifest `staging.json`. The production server (`KINGDOWN_STAGE` unset) refuses the staging Supabase project, database and origin; a staging server refuses the production ones.
- `tools/deploy.sh` with no flag checks a fresh `origin/main` in a temporary worktree and publishes nothing. Set `PLUGIN_TEST_DATABASE_URL` to a disposable loopback database whose name ends in `_test`. The path prepares the database, runs `npm test` and the default browser checks, then builds the combined tree with `npm run build:vercel`. When CI passed on that exact commit (`node tools/ci-green.mjs <sha>`: every check suite complete and green, and the combined commit status not failed, as merge-on-green requires), the script skips `npm test` and the web journey, because CI ran them on the same tree; the default browser checks (CI runs only four of them), the build, artifact, engine and live gates always run. No GitHub answer, a running or a failed CI means the full local run. When `wt` links the shared `node_modules`, the script replaces the link with its own `npm ci` installation, so no link path enters the bundle. It checks the engine archive and the compiled tree (`check:vercel`), then runs the web journey (`check:browser web-online`). While the plugin is parked, the website release runs no MCP protocol check and no plugin UI check. The step `production artifact` prints the sha256 of `static/index.html`, `static/sw.js` and each engine archive, and stops when an archive differs from the committed `engines/` file of the same name.
- `tools/deploy.sh --publish` checks the same tree, then publishes `kingdown-deploy/.vercel/output` to project `kingdown` with the pinned CLI and `--prebuilt --prod`. This one project serves the static site, the website routes (`/play`, `/g/…`, `/j`), the website API (`/api/*`) and internal jobs. The website API stays closed until the owner opens the 0016 `web_account_access` switch. The script checks the team and project before publication. Then the step `keep live assets` (`tools/deploy-keep-assets.mjs`) reads the live `/` and `/sw.js` without a cookie and follows each content-named file under `/assets/` that they name. It adds each file that the new build does not have to the publish copy, so a page of the old build can load its own chunks after the switch. The tested tree, `index.html`, `sw.js` and every file of the new build stay as built. The step stops before publication when a live file (also `/` and `/sw.js`) does not answer 200 with its content type, when the live build names a file of a type that the checks do not know, or when a live file has other bytes than the build file of the same name. It keeps one build back: a file that the live build kept from its own previous build goes. The step writes `assets/kept-files.json`, the list of the kept files. A rerun of the live build (its page is the new page, for example after a failed live check) keeps the files of that live list again. It then checks the live bundle, every public file, every file under `assets/` (kept files too) and the legal pages byte for byte, the app routes against the built `index.html`, and `/api/status` (`account_access` closed or open; unsigned account calls answer 503 while closed and 401 while open), plus the unsigned plugin endpoints at `https://kingdown.dev`. For a parked build (no `consent.mjs` in the function), the plugin live check sends GET and POST to each parked path and expects 404. For a build with the plugin, it preserves `authorization_id`, compares both metadata paths and the consent script, and checks one art file per format against the built bytes and headers.
- `tools/deploy.sh --configure <private-env-file>` sets the seven production server keys in `plugin-deploy/.env.example` for `kingdown`. Use the site origin, the new OAuth client UUID and an internal secret of at least 32 characters. The file must belong to this user and have mode 600. The script refuses mail keys and local check inputs. It sends values through standard input and withholds CLI write output. Set readiness to `1` only after the provider and audience checks pass. This command does not deploy.
- Legacy, until the old project retires: `tools/deploy.sh --setup-plugin` links the empty plugin project and checks its team and name. It prints the public project IDs and project details. It uploads no build and publishes nothing.
- Legacy: `tools/deploy.sh --configure-plugin <private-env-file>` sets the seven approved plugin production values. The file must belong to this user and have mode 600. Use the six original keys and `KINGDOWN_INTERNAL_SECRET` (at least 32 characters) once, with the old plugin origin and client, as unquoted `KEY=value` lines. The database URL must use the runtime role and `?sslmode=require`, with no other query option. Values pass through standard input; CLI output for each write is withheld. This command does not deploy. Set readiness to `1` only after the provider and audience checks pass.
- Legacy: `tools/deploy.sh --target plugin` requires `PLUGIN_TEST_DATABASE_URL`, a disposable loopback database whose name ends in `_test`. It prepares that schema, runs `npm test`, builds the Vercel artifact with the parked plugin surface in (`npm run plugin:build:vercel` passes `--chatgpt`, so the switch in `tools/chatgpt-plugin.mjs` does not park this tree), checks its compiled HTTP server, worker and MCP protocol, and runs `plugin-oauth`, `plugin-ui` and `plugin-ui-http` through the browser runner. It publishes nothing.
- Legacy: add `--publish` to the plugin command to release that tested artifact with `vercel@62.2.0 --prebuilt --prod`. The script checks the exact project ID and team ID before this step. It uses the project's production environment; no secret is passed as a CLI argument. It then checks discovery, the unsigned MCP challenge and the built consent script without a player session.
- A build that adds an engine must stop until its bundle and fixture are on `origin/main`. Set `KINGDOWN_ENGINES_DATABASE_URL` on the release command to check the engines of unfinished games. A `--publish` command stops before it makes a worktree when this read-only input is absent or does not name the production database (the project's direct `db.` host, or a Supabase pooler with a user that ends in the production project ref); a staging, loopback or other target is refused. Publish runs `engines-check.mjs --production`. A check-only run may skip, or use a local test database. It is not a production server key.
- Database backup and restore (release-safety ticket 01): In `plugin-deploy/`, `release-backup.sql` copies every public table in one repeatable-read snapshot, and `release-restore-games.sql` puts back the backup games, players, commands and invites in place, keeps newer games, leaves out the solo games of accounts deleted since the backup (as `delete_account` erased them) and their games that the deletion job ended (the live end stays), and refuses a backup whose games and commands disagree. Both run only by the owner's word; the ticket holds the order and the treatment of newer rows.
- Both live checks use `DEPLOY_LIVE_TIMEOUT_MS`. The default is 180000 ms for the site check and 120000 ms for the plugin check; each tries again every 5 s until the limit. Set 900000 ms for the migration window. Run the release command detached.
- The script takes no branch or commit. A commit that is not on `origin/main` cannot go live.
- Release helpers (`tools/release/`, each detached in tmux): `python3 tools/release/staging.py` deploys the current `origin/staging/first-game` to the staging preview after CI passes on that commit (evidence folder per run under `../evidence/staging-release/`); `tools/release/merge.sh <pr> <head> <reviewed head> [note]` records one complete independent review and merges on green; `tools/release/live.sh check|engines|publish` runs `tools/deploy.sh` on a fresh `origin/main` from the `release-live` worktree, the read-only engines check with the private runtime login, or the publish (it waits for green CI first, so the publish skips the local test run); `tools/release/release.sh <release pr> <head> [note]` runs merge, engines and publish in one go. Both worktrees (`release-staging`, `release-live`) keep their own `node_modules`; `tools/release/publishable-key.mjs <origin>` reads the public publishable key from the live bundle, so no key file is kept.
- Keep the release record: run `set -o pipefail; tools/deploy.sh --publish 2>&1 | tee <deploy-log-path>` detached. The deploy output log holds the source commit, the byte record, each step and both live-check results. The fresh worktree is the clean tree. The release log is `LOG.md` in `../evidence/production-release/`, relative to the main app checkout. Resolve the main checkout from Git's common directory, then pass the absolute log path to a writer. Check that the file and its prior release entry exist. Append to this file. It is outside the app repository and needs no app PR.
- The tool gate asks before a `vercel` command, a Porkbun API call or a browser visit to the live site or the Vercel dashboard.

## Secret files

- The folder `.secrets/` in the main checkout holds three files: `kaggle_api_token` (the Kaggle token), `oauth.json` (the OAuth keys) and `porkbun_api.json` (the Porkbun API keys).
- Git ignores the folder. Each file has mode 600. Never print, paste or commit a value.
- `tools/save-secret.sh NAME` stores the clipboard text as a new file in that folder and does not print the value.

## Parked: the ChatGPT plugin

The owner parked the ChatGPT plugin on 2026-10-28, so that the build is lean and the focus is the game (computer and multiplayer). The plugin was never sent to OpenAI for review, and no testers were invited.

- One switch: `CHATGPT_PLUGIN` in `tools/chatgpt-plugin.mjs` (now `false`). The server (`tools/plugin-server.mjs`) and the build (`tools/plugin-server-build.mjs`) read it.
- The parked build answers 404 for `/mcp`, `/authorize`, `/consent.mjs`, `/plugin-art/*` and three paths under `/.well-known/`: the two OAuth metadata paths and the OpenAI domain challenge (the list is `PARKED_PATHS`). It has no `board.html`, consent files, art or OAuth function paths.
- No change: the website, `/play/`, `/g/<id>`, `/j`, `/api/*` and `/internal/*`. The web pages still use `src/plugin/index.html`, `src/plugin/screens/*` and `PluginService`. The daily job still deletes old `plugin_boards` rows.
- All plugin source stays. Since 2026-11-01 CI runs no ChatGPT-only check (the owner: fixes took hours, so parked features leave CI): `plugin-oauth`, `plugin-ui-http`, the `chatgpt: true` server check and the WebKit `plugin-ui` step left. `plugin-ui` stays on Chromium, because its helpers also check screens the web game shares (the card detail sheet, Android hit sizes, the shell, the tablet power choice); WebKit no longer runs those helpers. To test the plugin by hand: `npm run plugin:build:chatgpt` builds the server with `chatgpt: true` into `plugin-server-chatgpt/` (never deploy that tree), and `npm run plugin:server:check -- plugin-server-chatgpt` runs the MCP flows over compiled HTTP and real PostgreSQL: friend code and join, restart and resume, board recovery and resource size. The named browser checks (`plugin-oauth`, `plugin-ui`, `plugin-ui-http`, `web-game`) build their own tree with `chatgpt: true`; `web-game` still runs in CI because it also plays the web seat. `plugin:check:protocol` runs the MCP server in memory. `plugin:build`, `plugin:server:check` and `check:vercel` check the parked build.
- The parked server does not need the ChatGPT OAuth setup. It does not read the two `KINGDOWN_PLUGIN_OAUTH_*` settings (the ready flag and the client IDs), it does not call Supabase OAuth discovery, and it does not check `kingdown_oauth.client_resources`. The website API needs only `SUPABASE_URL` and `SUPABASE_PUBLISHABLE_KEY`. The parked `server.mjs` has no MCP handler code. To bring the plugin back, all of the OAuth setup must work again before the server starts.
- A recovery rehearsal (`plugin:server:check` with a second, recovery directory) runs over MCP, so it stops with an error on a parked build. Build both trees with `chatgpt: true` to run it.
- The OpenAI review account cannot sign in with a password: `REVIEW_PASSWORD_SIGNIN` in `src/plugin/consent.ts` is `false`.
- Owner follow-ups outside the repository: the live Supabase before-user-created hook (`review-signup-hook.sql` in `plugin-deploy/`) and the table `password_accounts` in the schema `kingdown_auth` still exist. Turn the hook off and empty the table only by the owner's word.
- To bring the plugin back: set `CHATGPT_PLUGIN` and `REVIEW_PASSWORD_SIGNIN` to `true`, put the plugin protocol check and `check:browser plugin-ui plugin-ui-http` back in the website path of `tools/deploy.sh`, put the `plugin:build:chatgpt` steps, `plugin-oauth` and `plugin-ui-http` and the WebKit `plugin-ui` step back in `plugin-checks.yml`, and restore the ChatGPT text on the site and in the legal pages.
