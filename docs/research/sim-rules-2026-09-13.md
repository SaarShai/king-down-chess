# Rule questions after the buff set (2026-09-13)

The buffed campaign (`sim-buffed-2026-09-13.md`) adopted `archerMove=any` and `beastMove=any` and held the guard
pair, because `guardCaptures=pawns` with `guardStep=2` made an uncapturable pawn harvester in 43.7 % of games. This
pass asks three questions on that base, in **54 100 games and 79 minutes**. Which guard rule replaces the pair?
**Cap it — `guardCaptures=pawns` + `guardStep=2` + a new `guardCaptureLimit=1`** keeps 55 % of the pair's value and
removes the harvest completely. Which R4 toggle still changes the game once the movement buffs are in? **Only
`guardImmune`, of the five.** How do the designer's 2021 pieces compare? **The 2021 archer is 84 Elo weaker than
the 2017 one; the 2021 beast is worth exactly the same.**

## 1. Four additions to the lab

**`guardCaptureLimit: number`** (0 = no limit) caps how many pawns one side's guards take in a whole game. It is
the first rule that depends on the history of a game and not on the position, so it needs a counter. The counter is
**per side, not per guard**, and it sits beside `RULES` in `src/rules/rules.ts`, not in `Position`: `genPiece`,
`canCapture` and `isAttacked` take a bare `Uint8Array`, `src/ai/search.ts` makes and unmakes moves on its own
scratch board and never builds a `Position`, and a per-guard counter needs piece identity that a board of bytes
does not carry. `setRules` zeroes it, which every game already calls; `playGame` raises it after a real capture.
**Known ceiling:** inside the search the counter holds the *real* game's count, so a line that spends a guard
capture at ply 1 still believes it has one left at ply 3. The limit is exact for the move actually played.

**`--baseRule`, `--baseValues`, `--baseId`** move the control arm of a rule A/B, which was always today's game;
this pass needs it at the buffed base, or each arm is scored against a rule set nobody proposes to ship. `--baseId`
names the control arm's output, so the nine A/B runs sharing a base play it **once**: 36 000 games saved.

**The 2021 toggles:** `archerMove='fwdBack'`, `archerShots='forward3'`, `beastMove='diagFwdBack'`,
`beastCapture='diagForward'` (§4 says what each is). `forward3` is the first shot table **not closed under
negation**, which `isAttacked` relied on: the reverse lookup now walks every shot table negated and reads the
archer's and the beast's tables per colour. Each toggle has a test that flips it, asserts one consequence, and
re-runs the `isAttacked` / `genPiece('attacks')` cross-check on 300 random boards.

**The sampler now reads the run's rules.** `bishopsOppositeColours` decides which back ranks *exist*, and the
sampler runs in the main thread, which never called `setRules`, so the rule was invisible to its own run; `run()`
now applies the spec's rules before it builds the jobs. §3 says what that showed.

## 2. Guard alternatives

### 2.1 Odds against a knight

300 games (150 colour-reversed pairs) an arm, depth 3, `--eloPerPawn 64`, knight = 3.20 pawns, buffed values. The
odds army is `RNBQKBNR` with one knight replaced, so the archer and beast buffs are inert here.

| guard rule | pentanomial | score | Elo vs knight | Δ vs base |
|---|---|---|---|---|
| base — the guard as it ships | [81, 17, 40, 5, 7] | 0.233 | −207 ± 32 | — |
| (a) `guardCaptures=pawns`, `guardStep=1` | [64, 22, 48, 10, 6] | 0.287 | −158 ± 32 | **+49 ± 45** |
| (b) `guardStep=2`, `guardCaptures=none` | [82, 21, 31, 13, 3] | 0.223 | −217 ± 31 | −10 ± 45 |
| the pair (`pawns` + `step2`), for reference | [48, 32, 44, 15, 11] | 0.348 | −109 ± 34 | **+98 ± 47** |
| (c) the pair + `guardCaptureLimit=1` | [57, 35, 43, 5, 10] | 0.293 | −153 ± 33 | **+54 ± 46** |

Every row sits outside Muller's ±1.5-pawn band, so every implied value reads "< 1.70 pawns": a bound, not a number.
The Δ column adds the error bars in quadrature (conservative — the arms share openings). The base repeats §11 at a
new price, −207 ± 32 at G = 170 against −200 ± 33 at G = 185: the guard is blind to its own seed.

### 2.2 The harvester, counted

4 000 games an arm, 40 back ranks × 100 games, the same ranks and opening seeds in every arm, depth 3, base
`archerMove=any beastMove=any` with `--values A=280,L=310,G=170,M=330,S=215`; the control arm is shared.

| | base | (a) pawns, step 1 | (b) step 2, no captures | the pair | (c) pair + limit 1 |
|---|---|---|---|---|---|
| guard captures a game | 0.000 | 1.700 | 0.000 | **3.548** | 1.079 |
| games with ≥ 3 guard captures | 0.0 % | **21.5 %** | 0.0 % | **44.4 %** | **0.0 %** |
| dead-material endings | 4.8 % | 7.5 % | 6.0 % | **10.6 %** | 7.0 % |
| draw rate (paired Δ ± 95 %) | 0.260 | 0.319 (+0.058 ± 0.024) | 0.281 (+0.021 ± 0.014) | **0.377 (+0.116 ± 0.035)** | 0.310 (+0.050 ± 0.019) |
| decisive · White score | 0.714 · 0.521 | 0.647 · 0.518 | 0.690 · 0.521 | 0.587 · 0.515 | 0.660 · 0.529 |
| mean plies · guard moves | 127.9 · 9.76 | 133.2 · 13.79 | 130.8 · 11.85 | 137.5 · 19.77 | 132.1 · 14.28 |
| pawn survival | 27.9 % | 23.5 % | 27.9 % | 20.5 % | 25.6 % |

**The harvester is not only the pair.** `guardCaptures=pawns` on its own, with the one-square step, still reaches
three or more pawns in **21.5 %** of games and costs six draw points; §18 measured it at +4 ± 47 Elo in an odds arm
and read it as harmless, but it is not harmless where both sides have guards. **`guardStep=2` alone buys nothing:**
−10 ± 45 Elo, no captures, the same wall with legs, two draw points.

### 2.3 The recommendation

**`guardCaptures: 'pawns'` + `guardStep: 2` + `guardCaptureLimit: 1`.** It is the arm nearest a knight that leaves
no harvester: +54 ± 46 Elo, against +98 ± 47 for the pair and +49 ± 45 for pawns alone. One capture a side a game
holds the counter at 1.079 and takes the rampage share to zero by construction, while the guard still walks 14.28
squares and still reaches a pawn worth taking. It beats (a) on both axes — the same value inside the error bar,
21.5 % of harvest games gone — and it beats (b), which moves nothing.

Two honest costs. The guard is still **under 1.70 pawns** — no guard rule in two campaigns reaches a minor — and it
still adds **5.0 ± 1.9 draw points**, a third of the pair's 11.6. The fallback, if the designer will not pay those
draws, is (b) alone at +2.1 ± 1.4: the wall with legs. One design point the counters make plain: the guard's value
comes from the **first** pawn it takes, not the tenth — 55 % of the Elo from 30 % of the captures.

Fairy events a game, base → toggle: `archerChecks=false` takes checks 6.91 → 5.97 and maester long swaps
1.27 → 1.42; `guardImmune=false` takes maester swaps 5.28 → 4.87; `maesterLongSwap=false` takes long swaps
1.27 → 0.91 (the rest is the *adjacent* king swap). The other two move nothing.

**Only one toggle changes the game: `guardImmune=false`.** A guard any piece may take is worth four decisive
points, seven plies, two thirds of the ply caps and a third of the dead-material endings (4.8 → 3.6 %). It is §2
seen from the other side: the guard's whole weight is that it cannot be answered, walling or harvesting.
`archerChecks=false` is second and moves the wrong way — 5.5 plies longer, 1.5 points more ply caps; the
unblockable check is what ends a game with an archer on the board. `maesterLongSwap=false` measures **nothing**
against the 15–40 Elo `fairy-values.md` H9 predicted, and `promotionSet=standard` costs 0.1 of a legal move a
position and 0.02 promotions a game.

`bishopsOppositeColours=false` reads exact zeros because it is **not a game rule**: it decides which back ranks
exist. Of the 40 ranks, 38 are drawn identically under both settings and play byte-identical games; the two that
change (`BAMMKGBA`, `NKRNSBAB`) are the same-colour-bishop pairs the rule admits. Two-sample over each arm's own 40
ranks: White +0.001 ± 0.018, draws −0.008 ± 0.031. **Ignore this arm's "strong" flag** — with 38 of 40 paired
differences exactly 0, the interval collapses, not the effect.

two forward diagonals plus the square two ahead; the beast moves on the four diagonals and takes only the two
forward ones. Values are odds against a knight, 300 games an arm, depth 3, **2017 rules and today's values**, at

84 ± 45 Elo — one file to walk and three squares to shoot instead of eight, so it moves and shoots less than half as
often, while surviving just as much (72.7 % against 72.9 %). The beast reads **0 ± 42**: four diagonals of movement

twice as hard**, by different means — the 2021 set makes two pieces cheaper (the mining pass found pace tracks army
value), the buff set makes them active. **Neither moves White's edge**, the third campaign to say so. Today's
values stand in both 2021 arms, so a re-priced engine would read the 2021 archer **at most** this strong.

## 6. The cap made per guard (follow-up, same day)

§2.3 recommended `guardCaptures=pawns` + `guardStep=2` + `guardCaptureLimit=1`, and §1 shipped the limit as a
**per-side** counter beside `RULES`, with a known ceiling: the search read the *real* game's count, so a line that
spent a guard capture at ply 1 still believed it had one left at ply 3. The designer asked for the rule the sentence
actually describes — **one capture per guard, for its whole life** — so the state moved into the piece.

**Bit 5 of the piece byte.** Types own the low 4 bits and colour is bit 4, so `SPENT = 32` was free. `typeOf` and
`colorOf` mask it off; `landed()` sets it on the landing square and is the one function `makeMove` and the search's
`apply`/`applyQuiet` share, so make/unmake carries it exactly and **the search is no longer optimistic**; `zIndex`
hashes it (the spent half of the Zobrist table is drawn *after* the turn keys, so every key a board without a spent
guard uses keeps the value it had, and every stored run still replays byte for byte — five games of `abb-base`
checked); `toFen` writes it as `H`/`h`, so a position serialises. A promoted guard is a new guard. `GUARD_CAPS` is
gone, and `guardCaptureLimit` is now `0 | 1`: one bit holds one capture.

### 6.1 Odds against a knight

300 games (150 colour-reversed pairs), depth 3, `--eloPerPawn 64`, knight = 3.20 pawns, buffed base and values —
the same arms as §2.1, so the rows are directly comparable.

| guard rule | pentanomial | score | Elo vs knight | Δ vs base |
|---|---|---|---|---|
| base — the 2017 guard | [81, 17, 40, 5, 7] | 0.233 | −207 ± 32 | — |
| the pair, uncapped | [48, 32, 44, 15, 11] | 0.348 | −109 ± 34 | **+98 ± 47** |
| the pair + **per-side** limit 1 | [57, 35, 43, 5, 10] | 0.293 | −153 ± 33 | **+54 ± 46** |
| the pair + **per-guard** limit 1 | [60, 28, 45, 6, 11] | 0.300 | −147 ± 34 | **+60 ± 47** |

**The two caps are one arm apart:** +60 ± 47 against +54 ± 46, a 6-Elo gap inside a 47-Elo interval. Per guard is
the looser rule — two guards and any promoted guard each carry their own capture — and it buys nothing measurable,
which is the point: the rule got simpler to say without moving the balance.

approximate. `DEFAULT_RULES` in `src/rules/rules.ts` is this set; `RULES_2017` restores the rulebook game.
