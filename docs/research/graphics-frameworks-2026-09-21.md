# King Down Chess — rendering framework and sprite-route comparison

**Date:** 2026-09-21  
**Scope:** bounded comparison for the existing browser game. This report checks official engine capabilities and records the consequences for the current TypeScript/Three.js renderer. It does not benchmark devices, replace the renderer, or choose new artwork.

## Decision

Keep the existing `three@0.186.0` scene and `THREE.WebGLRenderer` as the production path. Treat refined voxel 3D, the current camera-facing billboards, and any angle-indexed sprite experiment as **rendering styles inside that engine**, not as reasons to rewrite the rules, input, animation, or HUD layers.

The current WebGL path already matches the game's needs: the renderer is WebGL2-based, the pixel look uses the official `RenderPixelatedPass` plus `EffectComposer`, the palette is a small custom `ShaderPass`, and the scene has an orthographic camera, orbit controls, voxel geometry, contact shadows, and imperative move/effect tweens. A framework migration would replace those seams without solving a demonstrated product problem.

Three.js's `WebGPURenderer` is a future experiment, not a drop-in switch for this build. Its official guide says it falls back to a WebGL2 backend, but it also requires a different `three/webgpu` entry and asynchronous initialization. More materially, `EffectComposer` passes are not supported there; post-processing moves to TSL/node composition, and custom `ShaderMaterial`, `RawShaderMaterial`, and `onBeforeCompile` paths need porting. The current palette pass and composer therefore make the WebGL renderer the lower-risk choice. ([r186 WebGLRenderer source](https://github.com/mrdoob/three.js/blob/r186/src/renderers/WebGLRenderer.js), [r186 WebGPURenderer source](https://github.com/mrdoob/three.js/blob/r186/src/renderers/webgpu/WebGPURenderer.js), [WebGPURenderer guide](https://threejs.org/manual/pages/webgpurenderer), [EffectComposer](https://threejs.org/docs/pages/EffectComposer.html))

## Verified local baseline

These are facts read from this checkout, separate from the engine comparison:

- `node_modules/three/package.json` reports `0.186.0`; `package.json` pins the matching `@types/three` range.
- `src/render/renderer.ts` constructs `WebGLRenderer`, `EffectComposer`, `RenderPixelatedPass`, `OutputPass`, `OrbitControls`, an orthographic camera, Lambert/toon materials, dynamic lights, ray picking, and the move/effect tween loop.
- `src/render/voxels.ts` loads the voxelized sculpt JSON and assigns each army a dominant `m`/`s` base/shade plus an `a` accent. Type-specific accent voxels remain part of the sculpt read.
- `src/render/sprites.ts` reuses the same piece types as camera-facing planes. Sprite textures use nearest filtering, disable mipmap generation, use `MeshBasicMaterial` with `alphaTest: 0.5`, and are hidden until loaded. The renderer supplies a separate flat contact shadow.
- `public/models/` contains sculpt models for the shipped standard and fairy pieces; `public/sprites/` contains pre-rendered army/type PNGs. The current code already lets a style switch between voxel and billboard pieces.

## Rendering style trade-offs inside Three.js

| Style | What it preserves | What it gives up | Recommendation |
|---|---|---|---|
| **Refined 3D voxel/sculpt** | Sculpt silhouette, depth ordering, orbit camera, dynamic lights, contact/depth shadows, and the existing move/effect choreography. Army colour can remain the dominant base/shade, with one or two type accents. | More mesh work and more sensitivity to lighting/camera readability; exact cost is a measurement question. | Keep as the canonical art route and tune silhouette, camera, light, and pixel settings before considering an engine change. |
| **One billboard per piece, current route** | Existing rendered PNG designs, fast asset iteration, and the same board/animation/input shell. | A plane has no side silhouette or true self-shadow. Its baked shading does not respond to orbiting lights; it needs a grounded contact shadow and a readable alpha edge. Current nearest/no-mipmap settings keep pixels crisp but can alias when the plane is minified or viewed obliquely. | Keep as an intentional alternate style or fallback. It is already implemented; do not build a second engine for it. |
| **Angle-indexed multi-view sprites** | Baked sculpt detail from several angles while keeping sprite draw/animation simplicity. | Every camera yaw/elevation bucket and every animation frame needs a corresponding image; switching buckets can pop. Depth, lighting, and shadows remain baked/faked, and the cards still need a ground pivot, contact shadow, alpha policy, and board-aware sorting. | Consider only as a measured, fixed-bin presentation candidate. Start with a small view count and a single elevation; treat it as an art/readability experiment, not an assumed low-end performance win, until view switching, memory, and frame-time measurements support it. |

### Multi-view cost model and failure modes

For RGBA8 textures, a first-order uncompressed GPU allocation estimate is:

`width × height × 4 bytes × views × animationFrames × armyVariants × typeVariants`,

plus atlas padding, staging/decoded copies, and any mip levels. A full mip chain is approximately another one-third of the base image allocation, but actual engine allocation and compression vary, so this is a planning estimate rather than a device measurement. For example, **11 visible types × 2 armies × 8 views × 6 frames at 192×192 RGBA8** is about **148.5 MiB** of base texel storage before atlas padding and extra copies; with a full mip chain the arithmetic estimate is about **198 MiB**. Reducing the frame or view count changes the product directly. Shared palette/tinting can remove an army multiplier only if the art can tolerate recolouring without losing the sculpt's intended accents.

The combinatorics are not just storage. A move hop, capture burst, archer shot, paladin self-burst, beast chain, and maester swap can animate a sprite frame sequence, but a camera rotation during that sequence also needs a deterministic view selection policy. Hard switching at a bin boundary can pop; crossfading two alpha cards can create halos and double silhouettes. A single camera-facing billboard avoids view pops but remains visually flat.

Grounding is a separate acceptance requirement: every view must share a consistent bottom pivot and footprint so the piece does not float as its aspect ratio changes. A transparent card should use a deliberate alpha policy. Alpha testing gives a crisp cutout and avoids translucent sorting, but it discards partially covered edge pixels; blended alpha gives softer edges but can expose sorting/halo issues around a shadow or a second card. Premultiplied and straight-alpha assets must not be mixed accidentally.

Mipmaps and pixel style pull in opposite directions. The current sprites explicitly use nearest filtering and no generated mipmaps, which protects hard pixel edges at the chosen scale. Multi-view cards will sometimes be smaller or more oblique than that chosen scale; nearest/no-mipmap sampling can shimmer, while ordinary linear filtering or mipmaps can soften palette boundaries. If the route advances, test a deliberately authored mip chain or a view/scale-specific atlas and judge the result at the smallest supported board size.

Lighting is the main visual distinction from the voxel route. A `MeshBasicMaterial` billboard can be tinted and filtered, but a point or directional light cannot reveal a newly lit side of the baked sculpt. Keep the separate contact shadow and use a simple selected/hover state; do not imply that a global palette pass makes a billboard physically lit.

## Staged recommendation and acceptance checks

1. **Keep the current production stack.** Preserve `WebGLRenderer`, `EffectComposer`, `RenderPixelatedPass`, the custom palette/dither pass, `OrbitControls`, and the existing voxel/sprite switch. Keep each army's dominant colour family stable and reserve one or two high-contrast accents per type so colour identifies army while silhouette/accent identifies type.

2. **Polish 3D before changing frameworks.** Check the sculpt silhouette and type read at the home camera, flipped camera, zoom limits, and the board's smallest intended viewport. Verify that the same piece remains selectable and that all current effects leave the correct piece on the correct square after animation.

3. **Keep billboards as a style/fallback.** Verify bottom contact, alpha edge, shadow placement, hover/selection state, camera orbit, and the smallest viewport. Record texture bytes, decoded texture count, frame time, and load time from the actual target matrix; do not infer them from engine marketing or from a desktop run.

4. **Prototype multi-view only if the art benefit is clear.** Use one elevation and a small azimuth set first. Accept the route only if view changes do not distract during orbit or animation, no card floats or leaks a halo, type/army read remains intact, and the measured texture memory/load/frame-time budget is acceptable on the target matrix. Treat any performance gain as an empirical result. If those checks fail, keep the single billboard or voxel style.

5. **Revisit WebGPU after the WebGL style is stable.** A useful experiment would port only the pixel/palette presentation to TSL/`RenderPipeline`, compare screenshots and input/animation behavior, and retain a WebGL2 path. It should be treated as a separate backend migration with its own acceptance evidence, not as a renderer constructor swap.
