## Real-time connection options, platforms and device support [`tc-realtime`]

Note: the shared web search budget ran out partway through, so I checked the last facts by fetching known primary URLs directly. For turn-based King Down, the board state stays in Supabase Postgres, which is already the match authority. A realtime channel only needs to say "revision N is ready". Clients then fetch state or apply the event. They resync after every reconnect. Lichess, Socket.IO, Ably, Supabase and SSE all use a sequence number with a full-reload fallback. Supabase Realtime is the simplest fit: it is already in the stack and uses the same accounts. Broadcast from Database can carry accepted commands on private channels. It has 72-hour replay and plan limits that easily cover a few hundred players. Vercel Functions now accept WebSockets, but only in public beta since 2026-06-22. Connections close at 300 to 800 s, fan-out needs Redis, and memory is billed while sockets are open. WebRTC needs signaling and TURN and gives no gain for chess. Hosted PartyKit shuts down on 2026-10-23. iOS suspends pages and in-app web views in the background, and sockets die without notice. So clients must resync on visibilitychange/pageshow and never trust readyState. Web Push on iPhone works only for Home Screen web apps. In ChatGPT, the MCP Apps spec lets connectDomains cover WebSocket, and ChatGPT claims full MCP Apps support. OpenAI docs mention only fetch, so wss:// in the widget needs a live test on every client. The 3-second tools/call polling works everywhere. Keep it as the baseline, make it adaptive, and try a Supabase "poke" subscription as an upgrade. Clocks must be server-side: deduct time at accept, use a Lichess-style lag quota, let clients claim a flag that the server verifies, and add a periodic sweep.

## Game backends, frameworks and open-source references [`tc-backends`]

I checked 17 products and references: 9 game backends (Nakama, Colyseus, boardgame.io, PlayFab, Photon, Unity Gaming Services, Rivet, Hathora, Edgegap, AWS GameLift), 4 open-source or engineering references (Lichess, OGS, PyChess, Chess.com), and 3 transport layers (Vercel WebSockets, Supabase Realtime, Cloudflare Durable Objects). The web-search budget ran out partway through, so I used WebFetch on primary pages for the rest.

Main result: no game backend fits King Down better than what it already has. At tens to a few hundred players, Supabase Postgres can stay the match authority, and the shared TypeScript engine can keep validating moves in Node. Nakama is strong but costs effort for King Down: its TypeScript runtime targets ES5 on the goja VM with no Node modules, it officially supports only CockroachDB, it keeps its own user table, and Heroic Cloud prices are not published. Colyseus is the best TypeScript fit for live rooms, but it needs a long-running Node process, and its rooms do not persist. Each remaining backend has at least one problem for King Down: it is only a relay, it is built for one engine, it is built for dedicated servers, or its status changed (Hathora is being shut down, Rivet now targets AI agents, and boardgame.io has had no release since 2022).

Three things are worth borrowing:
- **From Lichess:** versioned events with catch-up on reconnect, a socket layer that knows little about the game, and Glicko-2 ratings.
- **From OGS:** its clock and abandonment protocol.
- **From PyChess:** one process and one database are enough for a variant site.

Use these as designs, not code. Lichess, PyChess and the OGS web client are under AGPL licenses, and chessground (the Lichess board) is under GPL.

For realtime push, Supabase Realtime Broadcast is the simplest choice. Vercel WebSockets (beta) and Cloudflare Durable Objects are the next options if live play needs more.

## Database design and data processing for accounts, games, ratings and leaderboards [`tc-data`]

For King Down's expected load (tens to a few hundred concurrent players), one Supabase Postgres database can hold all multiplayer data. Redis, a separate game server and a separate event pipeline are not necessary at launch. The research checked Supabase, Vercel, Lichess (its source code), Woogles (its source code), Nakama, PlayFab, Steam, boardgame.io, Colyseus, Chess.com's public API, Redis and Upstash, Resend, Postmark and WebKit.

The common pattern has these parts:
- Each game row keeps the current state, and an append-only log keeps the moves.
- A per-player game table carries indexes, the rating before the game and the rating change.
- A small ratings table holds one row for each player and rating pool.
- Leaderboards are cached or computed from time to time, not computed on each request.
- Achievements use a table of definitions and a table of awards.
- Notifications are rows plus per-event channel preferences, and a queue sends them.

Postgres can end a game and update both ratings in one transaction. A status check makes this idempotent, and locking rows in a fixed order prevents deadlocks.

Supabase Cron (pg_cron) can run jobs every few seconds, so it can check clocks. Vercel Cron runs at most once a minute, which is too slow for live clocks.

Broadcast from the database (a trigger calls realtime.send on a private channel) is a better fit than Postgres Changes. Send only the revision. Each client then fetches its own seat's view, so hidden card hands stay hidden.

The Free plan stops a project after one week without activity and has no backups, so multiplayer needs Pro.

Today, deleting an account deletes the opponents' games too (on delete cascade). Lichess anonymizes games instead, and King Down should do the same.

**Product notes**

- **Supabase (Postgres, Auth, Realtime, Cron, Queues)**: One project can hold accounts, games, ratings, leaderboards, notifications and job scheduling. Pro is necessary: Free stops a project after 1 week without activity and has no backups. Use Supavisor transaction mode from Vercel. For game updates, use Broadcast from the database on private channels, not Postgres Changes. pg_cron can run jobs every few seconds, and pgmq gives a durable outbox. Edge Functions are too limited (2 s CPU) for the engine. WebSockets are in public beta since 2026-06-22, but each connection stays on one instance, so cross-instance fan-out needs Redis. Web Analytics costs $0.03 per 1,000 events on Pro. <https://vercel.com/docs/functions/limitations> <https://vercel.com/docs/cron-jobs/usage-and-pricing> <https://vercel.com/kb/guide/do-vercel-serverless-functions-support-websocket-connections> <https://vercel.com/docs/analytics/limits-and-pricing>

Each game document holds the compressed moves, the current position for variants, the clock history, and each player's rating, rating change and provisional flag. Glicko-2 updates after each game. Rating history keeps one point per day. Ranks are cached for 10 minutes. Matchmaking pools run in memory in waves and check block lists. Correspondence alarms run every 10 s, and an opt-in daily email digest exists. ## ChatGPT Apps / Plugins platform constraints for multiplayer [`tc-chatgpt`]

Inside ChatGPT, live play between two people works only while both boards are open. Async play has no notification path from ChatGPT to a player in normal Chat.

The board is an MCP Apps iframe with a strict CSP. The widget can call app-only tools without a model turn. It can also open its own connections to the domains you declare in connectDomains: fetch and SSE, and WebSocket by the spec. Two precedents use direct connections: OpenAI's own example uses SSE, and Cloudflare's chess tutorial uses a WebSocket. MCP Apps has no channel for the server to push to the view. The host can tear the view down at any time and replays the old tool result when it shows the board again.

MCP Events exists, but only in Work chats (web, and desktop in Cloud mode) and in dots, which need premium plans. An event starts a ChatGPT task. It does not update the board or send a push to the phone. PiP is documented, but OpenAI's newest extensions spec (2026-10-10) says ChatGPT does not support it. Do not depend on PiP.

Auth is OAuth 2.1 with PKCE. ChatGPT prefers client ID metadata documents (CIMD) and also supports dynamic client registration (DCR). Supabase's OAuth server signs players in as their existing website users, so the website and ChatGPT share one account. OpenAI publishes no numbers for tool-call timeouts or rate limits.

The directory has no explicit rules for user content or for chat between players. Plugins must suit users aged 13 to 17. They must not sell digital goods, and they must not be a weaker version of the website.

So a player learns that the opponent moved in one of three ways:
- A push ping, or a poll while the board is open, followed by a tool read.
- A fresh read when the board opens again.
- A King Down email or web push, sent outside ChatGPT.

## Identity, authentication and security across the website and ChatGPT [`tc-identity`]

Note on method: the shared web-search budget ran out on my first search. I did all the research by reading official pages, source code and rule texts directly. Dates are given where the pages show them.

Supabase can carry one account across the website and ChatGPT. Every token holds the same user UUID. ChatGPT tokens add a client_id claim and use the audience that King Down's hook sets. Anonymous sign-in, linking an identity later, CAPTCHA (Turnstile or hCaptcha), Realtime Authorization (RLS on realtime.messages) and grant revocation all exist, but each one has limits. Anonymous users are lost when they sign out. Supabase does not merge two accounts. Realtime keeps a permission until the JWT expires. The OAuth 2.1 server is in beta. Supabase Auth's CAPTCHA check covers anonymous sign-up. It does not touch social sign-in redirects or the OAuth token endpoint that ChatGPT uses, so Turnstile can protect guest sign-ins and the ChatGPT flow keeps working.

The repository has three gaps:
- Every foreign key on the shared match tables uses ON DELETE CASCADE. When a player deletes their account, the opponent's game history goes too. Lichess instead keeps such games and anonymizes the deleted player.
- Display names default to the sign-in provider's full name, and every signed-in player can read them.
- The ChatGPT consent page runs on a different origin with fewer providers than the website. This can create duplicate accounts.

The ChatGPT side has its own constraints. Tool-result `_meta` goes only to the widget and stays hidden from the model. The `openai/subject` field supports rate limiting. Traffic arrives from OpenAI egress IPs, so per-IP limits on /mcp would group many players into one bucket. Apple, Google Play and GDPR all require real account deletion. Anonymizing the deleted player's games meets this and keeps the opponent's history.

**Product notes**

- **Supabase Auth**: This is the identity base for both surfaces. Social sign-in, anonymous sign-in with is_anonymous, automatic linking by verified email, manual linkIdentity (beta), hCaptcha or Turnstile, per-IP rate limits, Before User Created and custom access token hooks, ES256 signing keys with JWKS, and Pro session controls all exist. Supabase never merges two accounts, never cleans up anonymous users, and keeps access tokens valid until expiry after sign-out. Read on 2026-10-10. Some docs pages contradict each other, for example the HS256 default versus 'asymmetric is default'. <https://supabase.com/docs/guides/auth/auth-anonymous> <https://supabase.com/docs/guides/auth/auth-identity-linking> <https://supabase.com/docs/guides/auth/rate-limits> <https://supabase.com/docs/guides/auth/signing-keys> <https://supabase.com/docs/guides/auth/sessions>
- **Supabase OAuth 2.1 server (MCP)**: In beta on all plans. Supports authorization code with PKCE and refresh. The consent UI lives at Site URL + authorization path. Optional DCR (the docs warn that any MCP client can then register). getUserGrants and revokeGrant exist. Tokens are Supabase JWTs with client_id. The docs do not mention CIMD, RFC 8707 or the iss response parameter, so keep the pre-registered client. Its /oauth/token route has no CAPTCHA middleware. <https://supabase.com/docs/guides/auth/oauth-server/getting-started> <https://supabase.com/docs/guides/auth/oauth-server/oauth-flows> <https://supabase.com/docs/guides/auth/oauth-server/token-security> <https://raw.githubusercontent.com/supabase/auth/master/internal/api/api.go>
- **Supabase Realtime**: Private channels are authorized by RLS on realtime.messages (SELECT to receive, INSERT to send, broadcast or presence). Permissions are cached per connection until the JWT expires. The database can broadcast with realtime.send or broadcast_changes, private by default. Pro allows 500 connections and 500 messages/s. Turn off 'Allow public access' to enforce private channels. <https://supabase.com/docs/guides/realtime/authorization> <https://supabase.com/docs/guides/realtime/broadcast> <https://supabase.com/docs/guides/realtime/limits>
- **OpenAI Apps SDK / ChatGPT plugins**: OAuth 2.1 with PKCE S256. CIMD preferred, then DCR or pre-registration. Per-tool securitySchemes. The linking UI starts from _meta mcp/www_authenticate. Multi-account with an optional openai/profile tool. openai/subject is meant for rate limiting. _meta in tool results stays hidden from the model. destructiveHint asks the user to approve. mTLS client certificate and egress IPs are available. Review needs a demo login. Content must suit ages 13 to 17. The pages show no dates and refer to spec 2026-07-28 and SEP-3149. <https://developers.openai.com/apps-sdk/build/auth> <https://developers.openai.com/apps-sdk/reference> <https://developers.openai.com/apps-sdk/guides/security-privacy> <https://developers.openai.com/apps-sdk/app-submission-guidelines>
- **MCP specification (2025-11-25) and MCP Apps extension**: Protected Resource Metadata is required. The resource parameter and audience validation are required. Token passthrough is banned. Sessions must not serve as authentication. Public clients need refresh-token rotation. The MCP Apps connectDomains covers WebSocket (connect-src) and defaults to no connections. The spec does not define how the iframe authenticates. <https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization> <https://modelcontextprotocol.io/specification/2025-11-25/basic/security_best_practices> <https://raw.githubusercontent.com/modelcontextprotocol/ext-apps/main/specification/draft/apps.mdx>

The @vercel/firewall checkRateLimit call accepts a custom key such as a user ID. BotID Basic is free, and Deep Analysis costs $1 per 1,000 calls on Pro. Both need your own server code and do not plug into Supabase Auth. Docs updated 2026-06 to 2026-08. <https://vercel.com/docs/vercel-firewall/vercel-waf/rate-limiting> <https://vercel.com/docs/vercel-firewall/vercel-waf/rate-limiting-sdk> <https://vercel.com/docs/botid>

Supabase supports it directly. <https://developers.cloudflare.com/turnstile/> <https://developers.cloudflare.com/turnstile/plans/> <https://developers.cloudflare.com/turnstile/get-started/server-side-validation/>
