# Research: Check browser replay against stored engines

Date: 2026-10-18. Source: `claude/release-candidate` at `442c5eb3` and main at `38a6bbff`. A reviewer checked the main claims against the code.

> Plan references marked `P:` or `web-adaptation/issues/NN` use the independent plan's ticket numbers. In the final plan: 06 → 10 (account entry), 08 → 13 (routes), 10 → 15 (public safety), 11 → 07 (engines), 12 → 08 (release evidence), 13 → 16 (test gate), 15 → 17 (release route).

## Question

can the current browser board code safely render and continue every supported stored account game, and what is the smallest contract for a game whose stored engine differs from the current one?

## Answer

Full browser support for every stored engine is **unverified**; the present checks do not prove it (Findings 4–9).
The server retains four engine versions and selects an engine from the save (Findings 1–3).
The browser uses current engine code for every draft and replay (Finding 4).
It can hide a server move or show a wrong draft state (Findings 5–7).
The server checks the full turn with the stored engine before it writes the game (Finding 8).
The plugin's present recovery does not close the browser gap (Finding 9).
Add an engine stamp to each View and permit local drafts only for versions with proof of browser support (Finding 10).
A game without that proof needs a tested continuation path before release; a refusal alone fails the plan (Finding 10).
Release also needs an approved report that every unfinished game has its engine in the exact release files (Finding 11).

2. **A save records the engine, rules, and full action history.** `MatchSave` holds the schema, engine stamp, setup, initial FEN, effective rules, revision, and commands. Each command holds its resulting FEN, ply, and status. The worker checks the stamp and replays each command. It rejects a different result. The account service copies the save stamp into `games.engine_fingerprint`. The store retains that column, the save in `state`, and a snapshot. Continuation selects the worker from `state.engine`, not from the database column. Sources: `src/match/index.ts:16–26,88–90`; `src/match/worker.ts:65,98–128`; `src/match/service.ts:95–98,180–189`; `src/match/store.ts:13–19,25,51–53,64–68`.

3. **The server has a small bridge for old snapshots.** For the two engines without public hands, the adapter adds new empty hand arrays to each snapshot. It accepts the four valid level names but removes the level option before it calls the old worker. The old worker keeps its built-in strength and still accepts time and depth bounds. The bridge does not change the save's engine or rules. Unknown engines fail with `MATCH_INCOMPATIBLE`; the current worker does not convert their saves. Sources: `src/match/index.ts:37–47,74–90`; `src/match/worker.ts:114–127`; `tools/engines.test.ts:14,36–64`; `docs/match-foundation.md:53–65`.

4. **Server archive tests do not prove browser support.** Each retained `.save.json:1` has setup `{}`, no powers or cards, and two actions: `Nb1-c3`, then `a7-a6`. All four use the same initial and resulting FENs. The archive test checks bundle hashes, fixture stamps, load, and one further legal action. It also checks the old snapshot bridge and a missing engine. It does not send these fixtures through the browser board. The board tests import current engine code and construct current-code positions. Thus, even a pass of these tests does not prove all old-game browser states. Sources: `engines/2675a7e6e32d635615350089a490902f4842ae26a7866d7123c6d95b49c60c5b.save.json:1`; `engines/a6f9ebec5f0f2d5ff0a7b24e726e196fd27821a5133176bcfda26b70de9b75cd.save.json:1`; `engines/a5750f9695e8f3cc341a69fb02bd709eed142ce7a36b2c69eaedd612fe1f5d16.save.json:1`; `engines/bab22e94d4df81591374763a7f3abe703c30534f80ce771ee3fe7e095dcec7da.save.json:1`; `tools/engines.test.ts:19–65`; `src/plugin/screens/board-model.test.ts:1–23,43–88,131–231,247–284`.

5. **The first-action filter can hide a legal server action.** The browser imports current `legalMoves`, `makeMove`, `status`, and `inCheck`. At turn start it intersects local actions with `View.legal`. It does not check that it can represent every server action. After one draft step it uses local actions alone. `applyLan` must also find the LAN in current local moves. A legal old-engine action can therefore disappear before a server request. A shared LAN can also have a different local effect. These are source-based risks; a failing retained game is **unverified** in this read-only check. Sources: `src/plugin/screens/board-model.ts:1–5,26–48`; `src/plugin/screens/board-model.test.ts:255–263`; `src/match/protocol.ts:85–92`.

6. **FEN display still depends on current rule code.** Castling rights and en passant need `classicChess` at FEN read time. The parser also applies current rights and en passant validity checks. `restoreDraft` and recent replay set rules before they parse FEN. Full history replay does not do this itself, but its present board caller does. The castling restore test covers stale global rules; it does not prove old-engine Classic or en passant replay. Saved rule fields overlay current defaults. They do not restore old movement code or old defaults for absent fields. Sources: `src/rules/setup.ts:175–207`; `src/rules/rules.ts:845–860`; `src/plugin/screens/board-model.ts:51–92`; `src/plugin/screens/board.ts:491–493`; `src/plugin/screens/board-model.test.ts:279–284`.

   Powers and cards have the same boundary. The FEN carries spent uses, marks, pending actions, and played-card state. The browser interprets them with current code. Card coins depend on hand order and spent bits; Mirror B has a special mapping. The old empty-hand bridge prevents a missing-hand failure, but it does not prove equal power effects. The board also computes check and threat marks locally, although View supplies `in_check`. Sources: `src/rules/setup.ts:80–92,115–155`; `src/plugin/screens/board-model.ts:20–23`; `src/plugin/screens/board.ts:298–305,339–349`; `src/match/index.ts:42–45`.

7. **Multi-action turns and draft results need more than a matching board.** Local code decides whether Haste, a free action, or another follow-up holds the turn. It decides when Send is available and can append `--`. A different engine can therefore cause an extra pass, an incomplete turn, or a missing follow-up choice. Tests cover Haste, free Freeze, Rally, saved half turns, staged results, and a Beast chain with current code. They do not compare archived workers with the browser. Sources: `src/plugin/screens/board-model.ts:33–48`; `src/turn.ts:41–47,65–79`; `src/plugin/screens/board-model.test.ts:131–231,247–263`.

   Repetition is a further limit, even with the same engine rules. The server's `Game` counts repeated positions. The browser draft calls position `status` without that count. Full View history exists, but `draftTurn` does not use it for repetition. Draft end words can thus differ from the server result. The final end card reads `View.result`, so a wrong draft message does not itself change the saved winner. Sources: `src/game.ts:26–27,50–62`; `src/plugin/screens/board-model.ts:33–38`; `src/match/protocol.ts:91–92,110`; `src/plugin/screens/end.ts:91–102`.

8. **The server protects stored game state.** A turn contains one to four LAN actions. The service loads the saved engine and applies the actions in order in a temporary worker. It refuses an action after the side changes, and refuses an unfinished human turn. It exports state only after these checks. Before it writes, the transaction checks the revision and receipt again under the game lock. A local draft cannot commit its own FEN or result. The server can accept the same LAN with a different effect, however; the draft can still mislead the player before submit. Sources: `src/match/protocol.ts:22–36`; `src/match/service.ts:93–114,295–321`; `src/match/store.ts:64–84`.

9. **The plugin has recovery, but no engine support check.** Recent replay requires a complete revision sequence and the exact final FEN. Full history replay also requires the exact final FEN. On a replay failure, the board can show the server FEN without the replay animation. It can retain old history; on a fresh load it can show no history. Equal final FEN does not prove equal intermediate states, move words, or future actions. FEN parsing and rule errors also have no explicit compatibility path in this board update. Sources: `src/plugin/screens/board-model.ts:64–92`; `src/plugin/screens/board.ts:482–517`.

   `INVALID_MOVE` clears the draft and reads the game again. Other move refusals can retain the draft if its base still agrees. A missing server engine gives HTTP 409 and `MATCH_INCOMPATIBLE`; the service message tells the player to start another game. This code is for a server save that cannot load. It is not a browser engine check. The plugin adapter and website HTTP adapter call the same game service. The web can reuse its safe server checks and recovery, but cannot claim full browser support by reusing this board unchanged. Sources: `src/plugin/screens/board.ts:202–209,499–507`; `src/plugin/app.ts:282–302`; `src/match/service.ts:95–98`; `src/match/protocol.ts:52–55`; `src/plugin/service.ts:35,43`; `src/api/http.ts:77–79,126–131`.

10. **Smallest proposed contract: add engine identity, then gate local computation.** This is a proposed change, not current behavior. Add `engine: string | null` to each View. Use the canonical saved stamp when an engine exists; use null before an engine starts. Full reads, command replies, and incremental reads carry the same immutable value. Keep the full save private. The server already stores this identity, but View omits it. Rules, FEN, legal LANs, and action history cannot identify the code that produces them. A final-FEN check also cannot prove future draft behavior. Sources for the gap: `src/match/store.ts:16–17`; `src/match/service.ts:180–186,447–462`; `src/match/protocol.ts:71–115`; `src/plugin/screens/board-model.ts:46–48,80–92`.

   The browser needs an explicit list of supported engine stamps with evidence for each. Do not compare a server-worker hash with a browser-file hash. The worker stamp includes search and worker code, so different stamps can still share browser behavior. The marker permits a support check; it does not prove support. Include it in the draft recovery key beside the full game ID, account, rules, and base FEN. An absent or unsupported stamp permits no local draft or reconstructed history. Keep server FEN, turn, check, legal actions, history LANs, and result as the display facts. Do not invent check marks, power previews, or replay frames with an unsupported engine. Sources: `tools/plugin-runtime-build.mjs:18–32`; `src/match/worker.ts:14–30`; `src/plugin/screens/board.ts:79,339–349`; `src/match/protocol.ts:83–114`; plan `spec.md:181–193`.

   The current View is enough for a basic server-state display where its FEN format is supported. It is not enough for a reliable engine-version gate or later draft steps. A server-only draft path could avoid a version gate for local rules, but it does not exist in this protocol. Do not load the archived Node workers into the browser: they import `node:worker_threads`. If a retained active engine fails browser checks, first require a tested supported client path. If none exists, a bounded server preview is the smallest next option to assess: load the stored worker, apply an unsent action prefix without a database write, and return its FEN, next legal actions, check, and turn-end state. Keep the final whole-turn commit and revision check. This preview is conditional work, not a finding that it is already needed. Sources: each archived `.mjs:1–2`; `src/match/protocol.ts:22–36,72–115`; `src/match/service.ts:93–114`; plan `issues/11-engine-compatibility.md:15–31`.

   Do not use `MATCH_INCOMPATIBLE` for a browser-only support limit when the server can still continue the game. Keep that code's server meaning clear. A notice and read-only board alone do not meet the active-game continuation rule. The plugin uses this same draft code, so “open the plugin” is not a proved alternate path. Sources: `src/match/index.ts:88–90`; `src/match/service.ts:95–98`; `src/plugin/screens/board-model.ts:1–5`; plan `issues/11-engine-compatibility.md:21–31`.

11. **The release needs both an engine report and continuation evidence.** The engines-in-use query groups unfinished `games` by `engine_fingerprint`. It excludes finished, aborted, and annulled games. It skips null engines only for waiting/setup games. If `games` does not exist, it checks playing `plugin_matches` saves instead. If both tables exist, it checks only `games`. The checker rejects malformed or absent engine files and uses a read-only transaction. It checks file presence, not save replay or browser behavior. Sources: `tools/engines-check.mjs:9–38`; `tools/engines.test.ts:77–101`.

   The deploy checks the engines inside the built function, which is the correct file set. But the query is optional: without its database setting, deploy prints that it skips the check and continues. A general deploy pass therefore does not prove active-engine coverage. The plan's stronger release gate must require the report and treat a skip as a stop. The build copies all archived `.mjs` files into the runtime; archive tests separately check their hashes and load fixtures. Sources: `tools/deploy.sh:190–195,208–225`; `tools/plugin-runtime-build.mjs:47–48`; `tools/engines.test.ts:19–35`; plan `issues/15-release-route.md:25–35`.
