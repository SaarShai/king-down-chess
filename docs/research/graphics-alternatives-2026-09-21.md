## What this means for the two rebuilt low-res pieces

Keep Three.js as the runtime and treat “pixel 3D,” fixed-angle isometric art, and angle-indexed sprites as separate **rendering styles**. The strongest path is a small Three.js 3D study using the existing orbit/effects and a carefully authored low-poly/painted pair, with the official pixel example’s camera/object snapping and texture sampling as the reference. QuietHours or Isomer can guide silhouette, per-face ink grouping, contour, and low-res re-authoring; their fixed projections should not be presented as orbit-capable runtimes. The Godot shader is a source for a depth/normal outline experiment, not a reason to change engines. Zdog is a fallback only for a consciously flat vector look.

The user’s authorization to rebuild two pieces makes a bounded A/B test practical: keep the existing board interaction and compare (a) actual low-poly Three.js pieces with pixel snapping, (b) a fixed-angle 2:1 sprite treatment derived from QuietHours/Isomer ideas, and, if desired, (c) a 12/16-direction bake. Evaluate silhouette/readability, grounding, selected-state feedback, orbit behavior, animation coverage, and texture memory on the supported browser/device set; none of these sources justifies an absolute “low-end is faster” claim.

## Multi-view sprite tradeoffs

- A view bake replaces per-frame geometry work with texture lookup and can make a deliberately authored silhouette stable at the chosen angles. It loses continuous parallax, arbitrary lighting/shadow response, and natural orbit between baked views; angle snapping or cross-fading must be designed.
- Storage grows with `view count × animation frame count × texture size × color channels`. A 16-direction bake is already 16 texture views before adding idle/attack/death or team variants. Atlas packing reduces bindings but does not remove texel memory; lower resolution and compressed formats change the art and must be measured.
- Sprites still need transparent textures, depth ordering/ground contact, selection outlines, and animation state handling. Premultiplied alpha, mipmaps, and filtering need deliberate settings: nearest filtering preserves hard pixels but can shimmer or alias when a view is minified; mipmaps help minification but can bleed transparent edges unless padding/alpha handling is correct.
- The current pass’s extra scene render and the sprite rig’s draw-call behavior should be measured separately. Fewer triangles alone does not establish a faster frame when the board, effects, texture sampling, or draw calls dominate.

## Test candidates and blockers

1. **First:** Two low-res Three.js meshes under the current orbit, tweens, selection/raycast, and pixel pass. Check that camera/object snapping preserves clarity without breaking animation or grounding.
2. **Second:** A fixed-angle QuietHours-style re-authoring of the same two pieces, rendered as an intentional sprite/thumbnail mode. Verify palette grouping, contours, alpha edges, and board contact.
3. **Third (optional):** 12- or 16-direction bake from the rebuilt pair. Measure view/animation atlas memory and draw behavior against the live meshes; do not assume the bake wins on older devices.
4. **Shader experiment:** Port the Godot depth/normal outline idea only if the existing Three.js pass cannot supply the desired edge language.

The remaining choices concern whether a fixed-angle mode is acceptable and how many animation states/views are needed. Guard and Archer were selected for the first rebuilds; a live prototype now compares the options. No shortlisted repository provides a ready-made chess asset pipeline or proves device performance for this project.
