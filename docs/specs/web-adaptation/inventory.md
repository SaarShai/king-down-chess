## What the earlier answer misses

1. Web sign-in, cloud save, local play, lessons, and the Workshop already exist. A new sign-in system or a replacement local game is not the smallest change.
2. The common server exists, but the release entry does not serve the web API. Several new features have no web route.
3. The screens depend on plugin app globals and tool results. Reuse needs a small shared client boundary. It is more than a new outer page.
4. The two clients have different state and save contracts. A local save, a server View, an unsent draft, and a pending command are different things.
5. The service worker can cache private GET responses if the API opens without a cache change. Server no-store headers alone do not fix the worker code.
6. MCP limits do not protect direct API calls. Reuse must preserve limits, identity checks, invite checks, and block behavior.
7. Most device fixes sit in plugin CSS and screens. Shared renderer fixes arrive on merge, but touch, zoom, and scroll fit need web work.
8. The website already has art, sound, lessons, and the end ceremony. Some plugin work reuses that work in the other direction.
9. Daily account games mean a move deadline. Today’s army means a local date seed. They are not the same feature.
10. Source tests and historical pass records are useful inputs. They do not prove the current release, a real phone browser, or a top-level web flow.
